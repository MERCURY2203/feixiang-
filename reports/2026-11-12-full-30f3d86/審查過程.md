## 3 執行記錄

1. 讀 GitHub main，確認提交。
2. 閱讀上述實作與文件，為檢查和寫入之間的競態設計暫停點。
3. 執行 scan.cjs：199 檔；76 JS 語法、47 JSON、30 WXML handler、31 WXSS 基本結構，failures=[]。這不是微信編譯器。
4. 執行原有 node tests/run.js：53/53；完整日誌保存在 evidence.zip。
5. 執行 full-cases.cjs：10 個案例成功重現。結果不依賴真實款項；沒有把假的雲端時間誤當實際審查耗時。
6. 依 package.json 範圍在獨立目錄執行 npm install --package-lock-only --ignore-scripts --no-audit --no-fund，再 npm audit --json。解析 158 個套件（依 npm metadata），13 個套件節點被標記，原始 lock 和公告完整附上。與雲端實際版本可能不同。
7. 對待確認的平台事務行為，查閱[騰訊官方 CloudBase 事務文件](https://docs.cloudbase.net/database/transaction)。沒有把僅違反本地先讀後寫慣例的程式，直接報成已證實的雲端運行錯誤。
8. 將問題按 P1/P2 與外部待驗證分類，附完整前提、位置、建議和驗收。

## 4 避免誤報的核對

- F1 以固定隨機輸出證明撞號時缺乏保護；沒有估算發生頻率。
- F2 不等於可偽造微信手機號，必須具備合法授權前提。
- F3/F4 證明特定交錯失敗，沒有說正常串行檢查完全失效。
- F5 是衝突規則同時保存，不宣稱已付款金額被追改。
- F6 已確認 bind 模板有 privacy-modal，問題在同意後沒有重試綁定，不是缺少同意元件。
- F7 動態重現客人清單，其餘相似頁面僅作提醒。
- F8 是未付款購物車數量被多刪，沒有多扣錢證據。
- F9 依「最多 5 張同時顯示」判斷，若店方要總排程數限制需先改規格。
- npm 公告不等於可達漏洞；依賴風險未當成第 11 個可利用 bug。
- 未改使用者已確認的協商退款政策，沒有擅自修程式或上線。
